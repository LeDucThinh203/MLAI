# EDUASSISTANT System Overview

EDUASSISTANT is Team 1's MLAI Hackathon 2026 submission for the VNG Track, Option A: The Escalation Referee.

## Scope

The only supported use case is `MILITARY_SERVICE_CONFIRMATION`: an internal workflow for processing student-status confirmation requests that may support military-service deferment paperwork. Its printout is an internal workflow record, not an official certificate. This application does not decide whether a person is legally eligible for deferment. `AUTO_APPROVE` means the internal workflow found enough trusted facts to process automatically; it is not approval from a military authority.

Live frontend: <https://edu-sp.pages.dev>
Judge page: <https://edu-sp.pages.dev/judge>

## Runtime shape

- Frontend: React and Vite, published on Cloudflare Pages.
- Backend: Java 8 source targeting Spring Boot 2.7, packaged as an executable JAR with Maven and served on port `3001`.
- Database: PostgreSQL through `DATABASE_URL`.
- Address extraction: Google Gemini first, OpenRouter fallback when configured, then deterministic parser fallback.
- SIS facts: Admin-managed internal demo registry. No external university SIS connector is present.

## Decision flow

1. The student submits a permanent-address claim.
2. Address AI returns parsed fields, confidence, provider/model, and call/fallback provenance.
3. The Rule Engine checks institutional trust provenance, identity, academic facts, address completeness, conflicts, and AI provenance.
4. It either routes the case to a human reviewer or marks it eligible for internal automatic processing.
5. For escalated cases, the human reviewer is the final internal decision maker. Reviewer actions, Rule Engine evaluations, and important Admin SIS changes are written to the audit trail.

AI supports address analysis, attachment OCR, and student guidance; it does not
own the final routing decision. The deterministic Rule Engine is the routing
authority. Legal eligibility and military-service deferment decisions remain
outside EDUASSISTANT.

The five escalation categories (`OWNERSHIP_UNCLEAR`, `FACT_UNKNOWN`, `DATA_CONFLICT`, `AUTHORITY_REQUIRED`, and `POLICY_OUT_OF_SCOPE`) are Team 1's implemented taxonomy, not a required Hackathon naming standard.

## Institutional trust

No external university SIS connector is present. Production configuration sets `ALLOW_ADMIN_VERIFIED_DEMO_SIS=false`, so `INTERNAL_DEMO_SIS` facts cannot authorize `AUTO_APPROVE`. A local demo may explicitly enable Admin-checked internal records; that label does not make them verified university facts. Future external facts require `sourceType=EXTERNAL_INSTITUTIONAL_SIS` and `verificationStatus=EXTERNAL_VERIFIED`.

Benchmark and Verify Harness fixtures use `SYNTHETIC_TEST_SIS` plus `TEST_VERIFIED`. They are accepted only when the caller passes an explicit deterministic test evaluation context. Production routes do not pass that context.

## Evaluation paths

| Path | Cases | Network or database writes | Purpose |
| --- | ---: | --- | --- |
| Verify Harness | 9 | None | Fast deterministic Rule Engine check |
| Fixed Synthetic Development Benchmark | 18 | None | Fixed development scenarios for escalation-policy metrics |
| Frozen Holdout | 36 | None | Manual final evaluation on a separate frozen synthetic set |
| Live AI E2E sanity check | 5 | Gemini and configured OpenRouter fallback | Optional address extraction check; separate from Track metrics |

The 18-case fixed synthetic benchmark writes its result and exact dataset SHA-256 to `benchmark/results/latest.json` and `.csv`. It is development evidence, not an independent or held-out score. The 36-case frozen holdout has a separate manifest and explicit manual runner; normal application requests and routine CI do not read or run it, and it is not claimed as externally authored. Read its latest result only from `benchmark/holdout/results/latest.json`; if absent, it has not been run.

## Integrity token and confidence limits

HMAC-SHA256 is an integrity authentication token that can detect changes when checked with the shared secret. It is not a PKI signature or a legal digital signature. The AI confidence score is generated by the model and has not been statistically calibrated on a production dataset.

## AI Agent

Authenticated students can open the Student AI Agent from the application shell. Reviewer and Admin accounts do not have Agent chat or Agent tools. It combines Gemini planning, OpenRouter fallback, an allowlisted RAG index, and typed student tools over existing application services. The internal SIS registry remains demo data; no external university SIS connector is provided.

The Agent's RAG sources are the student-service policy, student-agent FAQ, system overview, architecture document, and runtime policy registry. The root runbook is excluded because it can contain deployment instructions and credentials. RAG is not used for live case lookup. Every live read checks the authenticated student's ownership. Writes are previewed and require explicit confirmation; the server revalidates the student's role and target before using existing business routes. Agent output cannot decide legal eligibility or replace Rule Engine results.

Students can delete one Agent conversation. Deletion removes its conversation, messages, and pending Agent actions. It preserves case and SIS records, workflow audit records, RAG knowledge, and the student account; the audit trail retains a minimal deletion event without chat content.

Set `AGENT_ENABLED`, the `AGENT_*` bounds, `GEMINI_API_KEY`, and optionally `GEMINI_EMBEDDING_MODEL` / `OPENROUTER_API_KEY` in the backend environment. API keys stay server-side. If embedding or text generation is unavailable, lexical retrieval and safe fallback replies remain available.
